23. The FDX business workflow in one sentence

The entire product can essentially be described as:

An organization creates an event → uploads attendee identities and event photographs → FDX securely enrolls attendees' faces → processes the event gallery → identifies each attendee across the photographs → privately delivers each attendee only the photographs containing them.

The Super Admin sits one level above this and manages the organizations, users, storage, retention policies and health of the FDX platform.

This architecture also fits the direction of your existing codebase well: the repository currently has the local face-processing stack using RetinaFace/AdaFace, while the new branch already introduces separate Super Admin and College dashboard routes.

One architectural change I would make before implementing the backend is to remove College as a first-class backend concept and replace it with Organization everywhere. The frontend can display "College" or "Company" based on organization.type, but your APIs, database schema, JWT claims, storage structure, Kafka messages and permissions then remain identical for both
